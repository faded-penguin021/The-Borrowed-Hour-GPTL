## A1 — LLM output trust boundary — 2026-07-10 — fixed-2
- reviewed: `src/llm/parse.ts`, `src/llm/stream.ts`, `src/llm/schemas.ts`,
  `src/llm/zodConfig.ts`, `src/ambience/tables.ts#sanitizeAmbience`, consumption
  path in `src/context/gameLoop.ts`.
- findings:
  1. **No size bounds at the schema boundary** (fixed). Compliant providers cap
     output via `max_tokens`, but local endpoints (Ollama/LM Studio) and user
     proxies may ignore it. Oversized state fields persist into saves and are
     re-embedded in every subsequent turn's prompt (`formatStateForPrompt`),
     compounding the user's token cost; the history char-cap prunes middle
     messages but never truncates the oversized tail message itself. Fix:
     truncating clamps in `schemas.ts` (labels 1k, items 1k, prose 20k, lists
     50) — truncate, never fail, so a turn is never lost to verbosity.
  2. **Array-wrapped payloads unrecovered** (fixed). Some models emit
     `[{...}]` around the tool object; both GM parsers rejected it. Fix:
     `unwrapArray` in `extractJSONBlock` takes the first plain-object element.
- accepted as-is (with rationale):
  - `repairJSON` regexes (trailing commas, smart quotes) can alter *string
    contents* — acceptable because repair only runs after direct parse and
    balanced-slice both failed, i.e. on payloads already broken; distinguishing
    delimiter from content smart-quotes in broken JSON is not decidable.
  - Truncated (max_tokens-cut) JSON is unrecoverable by design at this layer;
    the game loop's corrective retry re-asks with escalated `max_tokens` and a
    schema-pointing diagnostic — verified present for both opening and GM-logic
    paths.
  - `console.warn` of raw malformed output: model output only, no secrets;
    consistent with THREAT_MODEL (only key material is barred from logs).
  - `stream.ts`: all provider-response reads are typeof-guarded; `logUsage`
    logs token counts only. `zodConfig.ts` jitless: correct, documented CSP
    interaction. Ambience input: enum-gated, events capped at 4 in
    `sanitizeAmbience`; schema enums derive from the canonical taxonomy.
- tests added: `parse-recover.test.ts` — "array-wrapped payload recovery" (4
  cases), "anti-runaway size clamps" (3 cases). Suite 30 → 37 cases.

## A2 — Turn pipeline correctness — 2026-07-10 — fixed-3
- reviewed: `src/context/gameLoop.ts`, `src/context/storyReducer.ts`,
  `src/context/GameContext.tsx`, `src/hooks/useLatest.ts`, `src/hooks/useAutosave.ts`.
- findings:
  1. **No synchronous reentry guard on turns** (fixed). `beginAdventure` had no
     guard at all; `submit`/`continueNarration` guard on the React `loading`
     flag, which flips only on the next render — and both await ambience setup
     before setting it. A double-click/double-Enter in that window raced two
     overlapping runs: two API calls billed, interleaved SET_ENTRIES /
     SET_HISTORY dispatches corrupting one another, and the first run's abort
     controller leaked (cancel only reached the second). Fix: a synchronous
     `inFlight` latch (with `runSeq` so a cancelled run's finally can't stomp a
     newer run's latch) wrapping begin/submit/continue via `exclusive()`;
     `undoLastTurn` also bails while in flight.
  2. **Stale-abort left a dangling user turn** (fixed). The 90s
     visibilitychange auto-abort called `controller.abort()` bare — no
     rollback — leaving the optimistic user message in history with no
     assistant reply (strict-alternation providers reject the next call) and
     the action entry with no narration. Fix: route through
     `loop.cancelRequest()` (abort + rollback + latch release).
  3. **loadSave's async illustration rehydration could clobber a fresh turn**
     (fixed). LOAD_SAVE dispatched immediately, then a floating promise
     re-dispatched SET_ENTRIES after IndexedDB reads; a turn submitted in that
     window lost its action entry. Fix: rehydrate before the single LOAD_SAVE
     dispatch; also cancel any in-flight turn before loading so its finalize
     can't land on the loaded game.
- accepted as-is (with rationale):
  - Reducer itself is sound: UNDO clamps frozen/pruned prefixes, LOAD_SAVE
    resets them, START_GAME resets to INITIAL_STATE.
  - Autosave timing: gated on `!loading && playing && entries>0`; every
    dispatch+setLoading pair sits in one synchronous block (React 18 batches),
    so no torn autosave snapshot.
  - `markMetaRevealed` maps a render-closure snapshot (not the updater form) —
    theoretical same-tick duplication only; reveal completions are serial.
- tests added: `gameLoop-unit.test.ts` — "run latch" (4 cases: double-begin,
  blocked second submit, cancel releases latch, undo blocked in flight),
  "loadSave" (2 cases: pre-dispatch rehydration, cancel-before-load).
  Suite 6 → 12 cases.

## A3 — Crypto & key custody — 2026-07-10 — fixed-1
- reviewed: `src/storage/encryption.ts`, `src/passphrase.ts`,
  `src/context/PassphraseContext.tsx`, `src/security/autoLock.ts`, key-path
  logging in `src/llm/client.ts` / `src/tts/*`.
- THREAT_MODEL conformance, claim by claim:
  - PBKDF2-SHA-256, 310k iterations, per-install public salt — **matches**
    (`encryption.ts` KDF constant; salt 16B random, persisted plaintext).
  - Non-extractable AES-GCM-256 session key — **matches** (deriveKey
    extractable:false; asserted by existing test).
  - Fresh 12-byte random IV per encryption — **matches**; now pinned by a new
    IV-freshness regression test (GCM IV reuse is the catastrophic case).
  - `enc:v2:` = `b64(iv).b64(ct)`, `enc:v1:` self-salted, unlock-time v1→v2
    sweep, best-effort per blob — **matches** (existing migration tests).
  - Salt-missing-but-v2-present fails loud, never loops the prompt —
    **matches** (`PassphraseContext` guards before `deriveSessionKey`, which
    would otherwise mint a fresh salt; helpers `hasKdfSalt`/
    `hasEncryptedV2Blobs` are unit-tested).
  - Passphrase consumed at unlock, only the CryptoKey retained — **matches**
    (React ref; sweep runs inside the unlock tick).
  - No key material in logs/errors — **matches**: `client.ts` scrubs the API
    key out of captured error bodies (`scrubSecrets`, 500-char cap); usage
    logs are token counts only; Gemini LLM calls use the `x-goog-api-key`
    header (not the URL).
- findings:
  1. **Absolute session cap armed at mount, not at unlock** (fixed). The 8h
     cap timer started when the provider mounted and fired exactly once — an
     unlock after that point (or any second unlock) ran with no cap at all,
     contradicting both the option's own doc ("upper bound on a single
     unlocked session") and THREAT_MODEL. Fix: `noteUnlocked()` on the
     controller, called at each successful unlock; cap re-arms per session.
- accepted as-is (with rationale):
  - `toB64` uses spread (`String.fromCharCode(...bytes)`), which would throw
    on ~64KB+ buffers — fine for its only use (API keys, <1KB); noted so a
    future caller doesn't reuse it for large blobs.
  - Google **TTS** adapter carries its key in the URL query (`?key=`) — the
    API offers no header form for browser callers; nothing logs request URLs.
    (Its origin is also absent from `connect-src` — picked up in A5.)
  - Plaintext (non-passphrase) key storage is a documented user choice; the
    encrypted path is opt-in by design.
- tests added: `encryption.test.ts` +1 (IV freshness);
  `src/passphrase.test.ts` new (6 cases: plaintext passthrough, cancel → null,
  v2 decrypt, wrong-key → WrongPassphraseError + lock, lingering v1 → error,
  post-migration re-read); `src/security/autoLock.test.ts` new (6 cases: cap
  armed at unlock not start, re-arm per unlock, hide-grace lock, foreground
  cancel, no-op while locked, stop clears timers).
